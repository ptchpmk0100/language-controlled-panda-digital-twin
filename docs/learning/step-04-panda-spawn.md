# Step 4 — Get the Real Panda Into the Physics Engine

## Objective

Graduate from the stand-in. Steps 2 and 3 proved the description → physics →
bridge → action pipeline on a hand-written one-joint arm; the pipeline was never
the deliverable, the Panda is. This milestone clears the obstacle that blocked the
real robot back in Step 2 — Gazebo rejecting the MoveIt Panda description — and
anchors the resulting model to the world.

Scope is deliberately narrow: **spawn and anchor only**. No controllers, no
bridge, no action. The arm is expected to fold under gravity at the end of this
step.

## The failure being fixed

Step 2 tried to spawn `moveit_resources_panda_description` and got a clean
`Entity creation successful.` in the ROS terminal while nothing appeared in the
world. The simulator's own terminal carried the real answer:

```text
link[panda_link0] has no <inertial> block
A model must have at least one link
```

That second line is misleading. There were twelve links. What Gazebo means is
that no link had **mass properties it could simulate** — a massless dynamic link
is invisible to a physics engine, so a model made entirely of them contains
nothing to integrate.

The diagnosis is a two-line count, not a guess:

```bash
grep -c "<link "     /opt/ros/jazzy/share/moveit_resources_panda_description/urdf/panda.urdf   # 12
grep -c "<inertial"  /opt/ros/jazzy/share/moveit_resources_panda_description/urdf/panda.urdf   #  0
```

Twelve links, zero inertials. The description ships that way on purpose: it is
built for motion planning and visualization, where mass is irrelevant.

## The fix: expand the xacro instead of writing inertials by hand

The obvious repair — hand-author twelve `<inertial>` blocks — would have invented
twelve sets of fabricated mass data. The sibling file in the same directory made
that unnecessary:

```text
urdf/panda.urdf        flat, autogenerated, inertials stripped
urdf/panda.urdf.xacro  the source, carrying real Franka CAD mass properties
```

**A `.urdf.xacro` is not a URDF.** Xacro is a preprocessor — macros and variables
over URDF — and its output must be expanded before any consumer can read it. The
flat file alongside it was generated by an older expansion that dropped the
inertial data. Running the preprocessor again recovers it:

```bash
xacro /opt/ros/jazzy/share/moveit_resources_panda_description/urdf/panda.urdf.xacro \
  > src/twin_description/urdf/panda.urdf
```

Result: 12 links, **11 with authentic inertials** — `panda_link1` at
`4.970684 kg` with a genuinely asymmetric inertia tensor, not a hand-rounded
guess.

### The twelfth link is not a bug

`panda_link8` has no inertial and needs none. It is an empty
`<link name="panda_link8"/>` welded on both sides by `type="fixed"` joints — a
pure coordinate frame marking the flange. Physics engines collapse fixed massless
frames into their neighbours rather than simulating them.

This is the distinction that matters: a massless link on a *movable* joint breaks
the solver; a massless link that is fixed-jointed on both sides is free.

### The mesh wall that never appeared

Step 3's handoff predicted a fight with `GZ_SIM_RESOURCE_PATH`, because URDF
meshes are normally referenced as `package://...` and Gazebo does not resolve ROS
package URIs. It never happened: xacro rewrote every mesh reference into an
absolute `file:///opt/ros/jazzy/...` path, which Gazebo opens directly.

That convenience is also this step's main debt — see Known limitations.

## The world anchor

A freshly spawned Panda has nothing holding it down; the whole robot is a rigid
body sitting in a gravity field. Bolting it to the ground is a `world` link and a
fixed joint, added by hand ahead of `panda_link0`:

```xml
<robot name="panda">
  <link name="world"/>
  <joint name="world_to_panda" type="fixed">
    <parent link="world"/>
    <child link="panda_link0"/>
    <origin rpy="0 0 0" xyz="0 0 0"/>
  </joint>
```

**The anchor's job is the base; the controllers' job is each joint.** They are
separate concerns, and confusing them makes the end state of this step look like a
failure. An anchored base with folding joints is exactly correct for a robot whose
motors are off.

## Problems worth keeping

### The spawn service reports on the request, not the outcome

`Entity creation successful.` means *the request was accepted*. Rejection is
logged by the simulator, in the simulator's terminal. This is the second time the
same trap has appeared in this project, so the working rule is now explicit: read
both terminals, and confirm the entity exists.

### Relative paths cross a process boundary and stop meaning anything

`ros2 run ros_gz_sim create -file <path>` hands `<path>` to the **already-running
Gazebo server**, which resolves it against *its own* working directory. A relative
`install/...` path is valid in the ROS terminal and meaningless to a simulator
started from elsewhere — producing another accepted request with an
`Unable to read file` on the far side. Always pass an absolute path.

### Do not edit `/opt/ros`

The system install is read-only by convention. The description was copied into
`twin_description` and edited there, exactly as the one-joint arm was.

## Verification

Headless, on Ubuntu 24.04 with ROS 2 Jazzy and Gazebo Sim 8.

```text
check_urdf panda.urdf
  robot name is: panda
  ---------- Successfully Parsed XML ---------------
  root Link: world has 1 child(ren)
      child(1):  panda_link0
          child(1):  panda_link1
              ...
```

The root link is now `world`, which is what an anchored robot looks like
structurally.

`gz sim -s -r empty.sdf`, then spawn with an absolute `-file` path:

```text
[INFO] [ros_gz_sim]: Entity creation successful.

Available models:
    - ground_plane
    - panda
```

The model is present — the claim Step 2 could not make. Link masses read back out
of the running physics engine:

| Link | Mass (kg) |
|---|---|
| `panda_link0` | 0.629769 |
| `panda_link1` | 4.970684 |
| `panda_link2` | 0.646926 |
| `panda_link3` | 3.228604 |
| `panda_link4` | 3.587895 |
| `panda_link5` | 1.225946 |
| `panda_link6` | 1.666555 |
| `panda_link7` | 1.465522 |
| `panda_leftfinger` | 0.015000 |
| `panda_rightfinger` | 0.150000 |

Two entries confirm the fixed-frame reasoning above rather than merely asserting
it. `panda_link8` does not appear at all — collapsed, as predicted. And
`panda_link7` reads 1.465522 kg where the description declares 0.735522 kg,
because `panda_hand` (0.73 kg) is attached by a fixed joint and DART welded the
two into one rigid body: `0.735522 + 0.73 = 1.465522` exactly.

Base pose after five seconds of stepping physics:

```text
  - Pose [ XYZ (m) ] [ RPY (rad) ]:
    [0.000000 0.000000 0.000000]
    [0.000000 -0.000000 0.000000]
```

Unchanged to six decimal places. The anchor holds. The arm joints, having no
controllers, fold under gravity — which is the cue for Step 5, not a defect.

The only simulator error is expected:

```text
[Err] Attempting to create a mimic constraint for joint [panda_finger_joint2]
      but the chosen physics engine does not support mimic constraints
```

DART does not implement URDF mimic joints, so the two gripper fingers will not
couple automatically. Nothing in this project drives the gripper yet.

## Lessons

**Read the error as a symptom, not a description.** "A model must have at least
one link" was true of nothing in the file. The message named a consequence; the
cause was one level down.

**Look for the generator before authoring by hand.** The correct mass data already
existed one file away. Hand-writing twelve inertial blocks would have been more
work and would have produced worse data.

**A prediction that does not come true is still worth recording.** The mesh-path
fight was expected and did not occur, for a specific reason. Knowing why it was
avoided is what makes it safe to change the generation step later.

## Known limitations

- **The committed URDF is generated, then hand-edited.** Re-running `xacro`
  silently discards the world anchor. The header records the command and the
  hazard; the durable fix is a small xacro wrapper that includes the Panda macro
  and adds the anchor, which is deferred rather than forgotten.
- **Mesh paths are absolute into `/opt/ros/jazzy/...`**, so the description is
  tied to a machine with ROS 2 Jazzy at the default prefix and
  `moveit_resources_panda_description` installed. That dependency is now declared
  in `package.xml`, but the paths themselves are not portable.
- **No controllers.** The arm cannot hold a pose or be commanded.
- **No joint state.** There is no `JointStatePublisher` plugin in this step, so
  joint angles cannot be measured — only link poses and masses can be inspected.
- **The gripper is inert**, and its mimic constraint is unsupported by DART.
- **Upstream finger masses are inconsistent** (0.015 kg against 0.150 kg, a
  tenfold difference). Not introduced here and not relevant to arm control, but
  recorded so it does not read as a transcription error later.
